# RepoDoctor v1.0 Öncesi Kalan Geliştirme Listesi

**Proje:** `@gucluyumhe/repodoctor`  
**Mevcut sürüm:** `0.6.0`  
**Hedef:** RepoDoctor’ı küçük, orta ve büyük projelerde güvenilir; CI/CD’de deterministik; güvenlik taramasında düşük false-positive oranına sahip; production kullanıma hazır bir v1.0 sürümüne taşımak.

---

## Genel durum

RepoDoctor 0.6.0 ile önemli bir seviyeye ulaştı. Aşağıdaki özellikler artık çalışıyor:

- Secret masking
- Dummy credential suppression
- Secret confidence bilgisi
- `.repodoctorignore`
- Baseline ve `--new-only`
- Dual health scoring
- TypeScript AST import analizi
- Scan coverage bilgisi
- Scan file/file-size limitleri
- `--fix --dry-run`
- Symlink/path traversal korumaları
- npm, pnpm, yarn ve bun CI generator desteği
- SARIF location bilgileri
- 152 başarılı test

v1.0 öncesinde odaklanılması gereken ana konular artık yeni özellik eklemekten çok **ölçek, doğruluk, güvenlik, deterministik davranış, dokümantasyon ve release kalitesi** olmalıdır.

# 1. P0 — Büyük repo benchmark ve performans sistemi

## Problem

Coverage ve limit sistemi çalışıyor; ancak 10.000, 50.000 ve 100.000 dosya seviyesinde gerçek performans henüz ölçülmüş değil. “Milliseconds” veya “her boyuttaki proje” iddiası benchmark olmadan garanti edilemez.

## Yapılacaklar

- [ ] 1.000 dosyalı fixture repo oluştur.
- [ ] 10.000 dosyalı fixture repo oluştur.
- [ ] 50.000 dosyalı fixture repo oluştur.
- [ ] 100.000 dosyalı fixture repo oluştur veya streaming benchmark hazırla.
- [ ] Her benchmark’ta dosya sayısı, toplam byte, peak memory ve süreyi ölç.
- [ ] Soğuk cache ve sıcak cache sonuçlarını ayrı ölç.
- [ ] Monorepo ve tek paket benchmark’larını ayrı çalıştır.
- [ ] Linux Node 18, 20 ve 22 üzerinde test et.
- [ ] Tarama limitine ulaşınca doğru warning üretildiğini kontrol et.
- [ ] Aynı dosyanın detector’lar tarafından tekrar tekrar okunmadığını doğrula.

## Önerilen komutlar

```bash
repodoctor benchmark ./tests/fixtures/1k
repodoctor benchmark ./tests/fixtures/10k
repodoctor benchmark ./tests/fixtures/50k
repodoctor benchmark ./tests/fixtures/100k --stream
```

## Coverage çıktısı şu bilgileri içermeli

```json
{
  "coverage": {
    "filesDiscovered": 50000,
    "filesScanned": 49800,
    "filesSkipped": 200,
    "bytesScanned": 238492012,
    "durationMs": 1840,
    "peakMemoryMb": 312,
    "scanLimitReached": false,
    "skippedReasons": {
      "ignored": 120,
      "binary": 30,
      "tooLarge": 50
    }
  }
}
```

## Kabul kriterleri

- [ ] Benchmark sonuçları CI’da raporlanıyor.
- [ ] Büyük repo taramasında memory leak yok.
- [ ] Tarama limiti aşılırsa kullanıcıya görünür warning veriliyor.
- [ ] `filesDiscovered`, `filesScanned`, `filesSkipped` ve `durationMs` her JSON raporunda bulunuyor.
- [ ] Büyük repo taramasında sessizce dosya atlanmıyor.
- [ ] README’deki performans iddiaları gerçek ölçümlere dayanıyor.

## Yapılacaklar

- [ ] HTML XSS testi ekle.
- [ ] SARIF injection testi ekle.
- [ ] Markdown injection testi ekle.
- [ ] Terminal escape sequence testi ekle.
- [ ] Malicious filename testi ekle.
- [ ] Newline içeren filename testi ekle.
- [ ] Symlink ile repository dışına erişim testi ekle.
- [ ] `../../outside` path traversal testi ekle.
- [ ] Çok uzun filename testi ekle.
- [ ] Çok büyük dosya testi ekle.
- [ ] Çok derin klasör yapısı testi ekle.
- [ ] Binary dosya ve bozuk UTF-8 testi ekle.
- [ ] Secret’ın JSON, HTML, Markdown, SARIF ve log’lara sızmadığını test et.

## Zorunlu fixture örnekleri

```text
<script>alert(1)</script>
</script><script>alert(1)</script>

..\\..\\outside
filename\nwith-newline
\u001b[31mred-terminal-text\u001b[0m
```

## Kabul kriterleri

- [ ] HTML çıktısı hiçbir user-controlled içeriği executable hale getirmiyor.
- [ ] Dosya yolları repository root dışına çıkamıyor.
- [ ] Symlink hedeflerine otomatik fix yazılmıyor.

# 4. P1 — GitHub Actions action’larını SHA ile pinleme

## Problem

Üretilen workflow’larda action’lar tag ile kullanılıyor:

```yaml
uses: actions/checkout@v4
uses: actions/setup-node@v4
uses: github/codeql-action/upload-sarif@v3
```

Tag’ler değişebildiği için supply-chain açısından commit SHA ile pinleme daha güvenlidir.

## Önerilen kullanım

```bash
repodoctor init-ci --pin-actions
```

Çıktı:

```yaml
uses: actions/checkout@<verified-commit-sha> # v4
uses: actions/setup-node@<verified-commit-sha> # v4
```

## Yapılacaklar

- [ ] Default workflow ile hardened workflow ayrımı yap.
- [ ] Action SHA’larını güvenilir bir sabit mapping dosyasında tut.
- [ ] Mapping dosyasının güncelleme tarihini göster.
- [ ] Tag yorumunu SHA ile birlikte koru.
- [ ] `--pin-actions` testi ekle.
- [ ] Workflow dosyasında unpinned action warning’i üret.
- [ ] Kullanıcıya stale SHA bilgisi ver.

## Kabul kriterleri

- [ ] Hardened mode’da tüm üçüncü parti action’lar SHA ile pinli.
- [ ] Action tag ve SHA uyuşmazlığı test ediliyor.
- [ ] Default mode davranışı README’de açıkça belgeleniyor.
- [ ] CI generator yanlış veya boş SHA üretmiyor.

# 7. P1 — Diagnostic ve exit-code sözleşmesini sabitle

## Problem

CI kullanıcıları için en kritik konu hangi durumda hangi exit code’un döndüğüdür. Bu sözleşme sürümler arasında değişmemelidir.

## Önerilen seçenekler

```bash
repodoctor --fail-on critical
repodoctor --fail-on high
repodoctor --fail-on warning
repodoctor --strict
repodoctor --ci --new-only
```

## Önerilen exit code sözleşmesi

| Exit code | Anlam |
|---:|---|
| 0 | Fail kriteri bulunmadı |
| 1 | Security veya reliability bulgusu fail eşiğini aştı |
| 2 | CLI kullanım/parametre hatası |
| 3 | Scan tamamlanamadı veya kritik I/O hatası oluştu |
| 4 | Rapor export işlemi başarısız |

## Yapılacaklar

- [ ] Exit code sabitlerini merkezi dosyaya taşı.
- [ ] `--fail-on` seçeneğini ekle.
- [ ] CLI kullanım hatası ile scan finding’ini ayır.
- [ ] Export hatasını scan sonucundan ayır.
- [ ] Baseline suppression sonrası exit code’u test et.
- [ ] JSON mode’da stdout temizliğini garanti et.
- [ ] İnsan okunabilir logları stderr’e yaz.

## Kabul kriterleri

- [ ] Aynı senaryo her çalıştırmada aynı exit code’u veriyor.
- [ ] CI’da warning ve critical davranışı açıkça kontrol edilebiliyor.
- [ ] `--json` stdout’u yalnızca JSON içeriyor.
- [ ] Hata kodları README’de belgeleniyor.

# Son öneri

v1.0’a ulaşmak için yeni detector sayısını artırmaktan önce mevcut özellikleri **ölçülebilir, test edilebilir ve stabil** hale getir.

İlk sırada şu beş konu yapılmalıdır:

```text
1. Büyük repo benchmark sistemi
2. Security self-test ve XSS/path edge-case testleri
3. Supply-chain analizinin derinleştirilmesi
4. GitHub Actions SHA pinleme
5. Coverage skip nedenlerinin ayrıntılandırılması
```

Bu beş konu tamamlandıktan sonra baseline, exit code, workspace, release ve compatibility maddeleri tamamlanmalıdır.

RepoDoctor v1.0 için en önemli kalite kriteri daha fazla özellik değil, şu garantidir:

> RepoDoctor bir projeyi taradığında hangi dosyaları taradığını, hangi dosyaları neden atladığını, hangi bulguların ne kadar güvenilir olduğunu ve CI’ın neden başarısız olduğunu kullanıcıya açıkça göstermelidir.
